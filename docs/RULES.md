# Rules

TraceState's policy is data. Each rule names a **check** (implemented by one
of the scanner wires), the **files** it applies to, a **severity**, and the
**framework controls** a violation is evidence against. The built-in pack has
35 rules; none of them knows anything about a particular project.

```bash
tracestate rules list              # what a scan will run
tracestate rules show TS-SEC-004   # everything about one rule
tracestate rules export > my.yaml  # the built-in pack, as a starting point
tracestate rules validate my.yaml  # check a rule file (exit 1 if invalid)
tracestate rules checks            # every check the wires implement
```

## Rule files

Rule files are YAML or JSON. A scan loads the built-in pack, then every
`--rules` file in order. A rule whose ID is already loaded replaces the
earlier rule, so you can re-grade or narrow a built-in rule without copying
the rest. `--no-default-rules` starts from nothing.

```yaml
version: 2
rules:
  # Raise the severity of a built-in rule for this organisation.
  - id: TS-CTR-005
    title: Image is not pinned to a version
    severity: high
    check: compose.mutable_image_tag
    files: ["**/docker-compose*.yml", "**/compose*.yaml"]

  # An organisation-specific rule, no Go needed.
  - id: ACME-LOG-001
    title: Customer IDs must not be logged
    severity: medium
    check: regex.match
    pattern: 'log\w*\.\w+\(.*\bcustomer_id\b'
    files: ["services/**/*.py"]
    exclude: ["**/tests/**"]
    frameworks:
      DPDPA: [s.8(5)]
      ISO27001: [A.8.15]
    remediation: Log the request ID instead.
```

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique ID. Upper-case with dashes (`ACME-LOG-001`), so suppression comments can name it. |
| `title` | yes | One line, shown in every report. |
| `severity` | yes | `critical`, `high`, `medium`, `low` or `info`. |
| `check` | yes | What to run: one of `tracestate rules checks`. |
| `files` | yes | Globs relative to the scan root. `**` crosses directories; `{a,b}` alternates. |
| `exclude` | no | Globs to skip even when `files` matches. |
| `pattern` | for `regex.*` | Go regular expression (RE2 syntax). |
| `redact` | no | Mask the matched text in evidence (use it when the pattern matches personal data). |
| `description` | no | Longer explanation, shown by `rules show` and in reports. |
| `frameworks` | no | Map of framework ID to control IDs. Framework IDs: `ISO27001`, `DPDPA`, `PCI-DSS`, `HIPAA`, `NIST-CSF`, `SEBI-CSCRF`, `OWASP`, `CWE`, `CIS-Docker`; others are allowed and reported as given. |
| `remediation` | no | What to do about a finding. |
| `references` | no | URLs. |
| `online` | no | The check needs the network; it runs only with `--online`. |

Every scan records the SHA-256 of the rule files it loaded, in the report and
in the ledger, so a result can always be tied back to the exact policy.

### Pattern rules

Two checks exist so that policy can grow without code:

- `regex.match`: a file matching `files` must **not** contain `pattern`. One
  finding per file, at the first match, with the number of matches.
- `regex.absent`: a file matching `files` **must** contain `pattern`, for
  example a licence header or a `USER` line.

Anything that needs structure (which service a compose key belongs to, which
Dockerfile stage is final, whether a lockfile pins a range) is a wire; see
[CONTRIBUTING.md](../CONTRIBUTING.md).

## Suppressing a finding

Put `tracestate:ignore` in a comment on the line, or on a comment-only line
directly above it. Name the rules to keep the suppression narrow:

```python
# tracestate:ignore TS-SEC-003 test fixture, not a real key
FAKE_KEY = "sk_test_placeholder_for_unit_tests"

API_URL = "http://localhost:8080"  # tracestate:ignore TS-NET-004
```

A bare `tracestate:ignore` suppresses every rule on that line. Every report
and the ledger count suppressed findings ("3 suppressed"), so a suppression
is visible to whoever reviews the scan.

To leave whole paths out, pass `--exclude 'vendor/**'` (repeatable) to
`scan`, or add `exclude` to a rule.

## Severity and exit codes

`scan --fail-on high` (the default) exits 1 when any finding is at or above
`high`; `--fail-on none` never fails on findings. Exit code 2 means the scan
itself failed (bad flags, an invalid rule file, an unreadable target).
